# pm-AMM feasibility spike

Recommendation: **GO for a devnet hackathon trading prototype; NO-GO for immediately replacing the only trading path.** The isolated SDK integration creates a funded rain market and executes both sides, but the application model changes from fixed cover purchases to outcome tokens with moving prices. Migration needs deliberate quote, position, Collect, liquidity and resolver work. A known historical outcome proves mechanics only; it says nothing about demand, weather pricing or profitable liquidity.

## Scope and reproducibility

Branch `pm-amm-spike`, based on `origin/web-app-and-landing`. No existing web, mobile, server or Anchor behavior was changed. Runtime is CommonJS, SDK pinned to 0.2.0 with a separate lockfile under `spikes/pm-amm/`. Only devnet RPC and the devnet mUSDC mint are configured. API signatures and units were checked against the [SDK reference](https://predict-pm-amm.dev/llms.txt). No deployment, push or PR.

Run `npm ci --prefix spikes/pm-amm`, `npm --prefix spikes/pm-amm test`, then `npm --prefix spikes/pm-amm run run`. The first run funds two fixed wallets, creates one market and trades; it prints the expiry. Run again after that time to fetch NOAA again, resolve and claim, including redeeming the creator’s winning tokens distributed by `claimLpResiduals`. `npm --prefix spikes/pm-amm run resolve` runs the resolver separately. Existing run checkpoints prevent new markets on rerun. To reproduce this particular run, use its committed evidence; private signing keys are deliberately unavailable in git.

Keypairs live in `~/.config/skyhedge-pmamm/{creator,no-trader}.json`, files mode 600, directory created mode 700. Only public addresses appear in evidence. Faucet attempts are persisted before requests; no automatic retry or wallet rotation. Ambiguous chain sends require manual reconciliation before clearing their attempt marker. Back up the external keys if further interaction with this market is wanted.

The copied `pm-amm-helpers.ts` is from the [official helper URL](https://predict-pm-amm.dev/helpers/pm-amm-helpers.ts); `helpers.cjs` is its CommonJS transpilation, generated with the local esbuild dependency. Regenerate using `cd spikes/pm-amm && npx esbuild pm-amm-helpers.ts --platform=node --format=cjs --outfile=helpers.cjs`. This retains upstream `quoteSwap`, `minOutput` and time-accrued price calculations. Swaps use raw six-decimal amounts and a 1% minimum-output tolerance.

## NOAA strike and trust

Market: `NYC Central Park rain >=1mm 2026-10-01 (NOAA)`.

[NOAA NCEI daily-summaries query](https://www.ncei.noaa.gov/access/services/data/v1?dataset=daily-summaries&stations=USW00094728&startDate=2026-10-01&endDate=2026-10-01&dataTypes=PRCP&units=metric&format=json&includeAttributes=true)

Station USW00094728, published station observation day 2026-10-01, PRCP `"0.0"` mm, attributes `",,1,2400"`, computed total **0.0 mm**, threshold **>= 1.0 mm**, outcome **NO**. The date denotes NOAA's station daily record; this does not claim a UTC midnight interval. The short market trading window is separate from the historical observation day. Both sides intentionally traded a known outcome to exercise mechanics.

The resolver requires exactly one matching station/day, a nonnegative numeric PRCP, and a blank NOAA quality flag. It refuses absent, duplicate, malformed or quality-flagged data. It evaluates tenths of a millimeter and applies an inclusive threshold. It checks market name, authority and collateral, and chain time past expiry, before sending resolution. The JSON evidence contains the fetched URL, raw response, parsed values, fetch time, SHA-256, computed total, side and transaction signature. Anyone can re-fetch and compare; a hash records the response seen, not NOAA authenticity on chain.

This is still a **single trusted creator key**. NOAA data can be revised. There is no dispute window, independent oracle consensus, enforced source commitment or on-chain validation of the station/threshold. Market names are descriptions, not machine-enforced weather terms. Missing data causes this resolver to stop; a production unavailable-data policy and any refund path require design because manual binary resolution alone does not provide the existing app's unavailable-data lifecycle. A compromised authority can resolve the other side. An outage can leave funds waiting.

## Observed integration results

The full machine-readable record is [devnet.json](../spikes/pm-amm/runs/devnet.json). Both faucet requests returned HTTP 200, each reporting 1,000 mUSDC and 0.2 devnet SOL; no SOL airdrop was needed. The first 300-second create failed with program error 6012. Its signature and program logs were recovered from creator history; no creator markets existed before retry. The successful create used 600 seconds to allow timing headroom. The failed transaction consumed 0.000005 SOL in fees and created no market. Its logs explicitly report InvalidDuration; the exact 300-second SDK request failed while 600 seconds worked. Client/chain timing is a suspected cause, not independently established.

The successful create's finalized transaction payer balance decrease was **0.035382160 SOL**, including account rent and transaction fee. This excludes the earlier failed create fee. It seeded **50 mUSDC**. This is one sample, not a universal creation-cost guarantee.

YES input **5 mUSDC**: helper YES price moved **0.5000000010 → 0.5305719684**. NO input **5 mUSDC** from the second wallet: YES price moved **0.5305719684 → 0.4980777888**. These are fetched, time-accrued helper prices before/after each confirmed trade, not executions at a fixed price. Quotes were 9.509143 YES and 10.089491 NO respectively, with a quoted 0.1 mUSDC fee each. Finalized token receipts were **9.509144 YES** and **10.089214 NO**. The small quote/output differences demonstrate why a nonzero slippage tolerance matters. Each first trade spent **0.002981880 SOL**, including token-account rent and fees. The creator also received its fee share when buying YES, so its net mUSDC decrease differs from the gross 5 mUSDC input. Even these small trades materially move a 50 mUSDC pool.

The market resolved NO after expiry; the second wallet redeemed **10.089214 mUSDC**. `claimLpResiduals` succeeded and minted **50.290854 YES** and **49.710785 NO** to the creator (receipt balance differences), with no direct mUSDC transfer. A second `claimWinnings` call by the creator then redeemed **49.710785 mUSDC**. Thus a successful residual claim alone does not complete LP collateral recovery. The recovered collateral was below the 50 mUSDC seed; creator fee income totaled **0.1 mUSDC** across the two buys (measured mUSDC balance changes), separate from LP redemption and the creator’s losing YES trade. Run `npm --prefix spikes/pm-amm run verify` to refresh finalized transaction receipts and market state; receipts include actual pre/post token balances and fees.

## Migration effort estimates

All durations below are **engineering estimates in working days**, for one engineer familiar with this repo, assuming a devnet-only hackathon scope and funded markets. They are not measured delivery times. External review, real-value readiness and unpredictable RPC/NOAA outages are excluded.

Shared backend work: **4–7 days estimated**. Replace market/catalog reads and transaction builders (1–2), replace fixed quote/position/claim semantics with token balances and fee-aware prices (1–2), add a pm-AMM resolver/evidence job and decide unavailable-data policy (1–2), verify end-to-end and disable old purchase routes (1). Evidence: `server/services/unsigned-tx.ts` builds the existing program's open-position, payout, refund and LP actions; `settlement.ts` atomically submits weather evidence and settles the custom program; `ghcnd-daily.ts` already screens station observations; `mobile-api.ts` exposes shared market/claim reads. NOAA utilities can inform an adapter, but their existing chain writes cannot resolve pm-AMM unchanged.

**Web only trading path: 8–13 days estimated total**, including shared backend 4–7 plus web 4–6. `client/src/lib/solana.ts` reads SKYT and signs wallet-adapter transactions; `components/line/line-protect.tsx` submits fixed-cover `open_position`; `pages/dashboard.tsx` includes admin seeding, buying and claims. Reuse signing and display structure, replace SKYT balances, catalog identifiers, price inputs, receipts and Collect readiness with mUSDC and outcome-token semantics (2–3); add burner onboarding, minimum-output review and stale-quote handling (1–2); verify wallet, liquidity and claims plus remove all old trading entry points (1). This covers React client trading routes; the separate Expo web artifact built by root `build` also needs the mobile UI work if it remains user-accessible. A root build ships both, so replacing only `client/` is insufficient for a site-wide exclusive path.

**Android/Seeker only trading path: 10–17 days estimated total**, including shared backend 4–7 plus mobile 6–10. `mobile/src/open-position-tx.ts` hardcodes the old instruction discriminator, PDAs and SKYT mint and mentions Hermes Buffer constraints; replace its on-device transaction construction or consume a new server builder (2–3). `wallet.ts`, `wallet-send.ts` and `wallet-auth.ts` already implement MWA signing/reauthorization, account checks and minContextSlot: preserve these while testing SDK transaction compatibility on an actual device (1–2). `positions.ts`, `line-submit.ts`, `line/use-discovery.ts` and `line/CoverDetail.tsx` assume fixed cover, duplicate-position blocking and existing claim actions: adapt token positions, repeated buys, pricing, mUSDC and Collect (2–3). Device lifecycle, funding and failure-path verification (1–2). No device build or hardware test was performed in this spike. Native SDK loading/polyfills remain unproven; server-built unsigned instructions reduce that risk. If both clients migrate together, shared backend days are incurred once, not twice.

## Burner wallets, liquidity and risks

The [official burner kit](https://predict-pm-amm.dev/burner/README.md) provides browser-local devnet keys and faucet funding with player role. Local storage is suitable only for disposable devnet funds; browser deletion loses signing access. Keep the market creator separate from players. Android should retain MWA for real user wallets; an optional demo burner needs secure storage and lifecycle/recovery work rather than copying browser localStorage. The spike uses external file wallets and proves neither browser burner UX nor native signing.

Liquidity must be budgeted per station, strike and date window; fragmentation requires funded LP inventory and a market creation policy. The measured 50 mUSDC seed and roughly three percentage-point movements per 5 mUSDC trade are enough for a mechanics demo, not evidence of adequate hedging capacity. Time-decaying liquidity changes quotes; a larger/longer-lived market needs fresh measurements, not extrapolated promises. LP residual recovery is measured above; it is not guaranteed capital preservation. The trusted resolver, missing-data policy, single key custody, SDK dependency advisories, new collateral, faucet limits, RPC rate limits and untested mobile runtime are blockers to an immediate exclusive-path switch.

`npm audit` reports dependency advisories in the isolated dependency tree, including high severity paths through Anchor, SPL token and bigint-buffer; no automatic dependency upgrades were applied to the pinned spike. The pure JS bigint fallback warning was observed. Neither code audit nor protocol economic security was established.

The [hackathon kit](https://predict-pm-amm.dev/hackathon.md) asks for an accessible working app; this spike is deliberately scripts only under the requested scope. A GO for a hackathon prototype requires subsequent UI integration, adequate seed funding and a resolver operating plan before the stated December 5, 2026 deadline. SkyHedge's weather hedging audience includes individuals and businesses such as farmers, events, aviation and street vendors; outcome trading needs understandable payout units for each.
